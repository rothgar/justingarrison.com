It's September 2026 and we're going through another wave of "what is software engineering" angst.
These have been coming every 4-6 months since ChatGPT launched and have ranged from RAG, one shots, gas towns, agents, escapes, and "open" is having a moment.

Open weight models have caught up to be good enough for a lot of software lifecycle tasks.
Open harnesses are still in flux, but there are some patterns about what shape they should have and what layers each part of the system should be responsible for.

This is where [Kimchi](https://kimchi.dev) sits.

An open source harness built on [Pi](https://pi.dev) with some vibey functions.
And Kimchi, the service that manages access, measurements, and runs open weight models.

Here's a video review to see both components in action.

## Some neat features

Kimchi leans into the vibe of vibe coding and builds a plugin with the command `/ferment` right into the harness.
This is designed to require minimal confirmation and prompting and gives you the appearance of productivity by smashing features with minimal effort.

This idea has come in the form of "loop engineering" with Claude, but ferment is more flexible in how much it will build for you.
After using it for the past couple months on a few different personal projects I don't think it's very useful for the big things.
Like most mid-tier LLM models, it does better with smaller, directed instructions that don't meander too much through a codebase.

It works great once you know what to do, but that's the problem with software long before LLMs existed.

The harness feature I was more impressed by was the client-side, multi-model routing.
It comes with some default roles and models that complement those roles.
Orchestrator, planner, builder, and judge are some examples and it worked surprisingly well.

I'm used to the Claude code method of going into plan mode and ask a bunch of questions.
Then go into build mode and push enter a bunch of times.
You can't change models or thinking or you risk needing to re-inject the entire context eating precious tokens.

Kimchi's model routing and automatic roles made all of that invisible.
I didn't even know it was happening until I checked my usage in the app.

## Optional self-hosting

Kimchi supports `OLLAMA_HOST` [out of the box](https://docs.kimchi.dev/docs/coding-ollama) with no additional configuration.
If you have an ollama server running and export the environment variable, kimchi can use your local models automatically.
That's really cool!

I'm not a big fan of Ollama, but I am a big fan of self-hosted models.
As smaller models become more useful, I really want to see more harnesses support this type of configuration by default.

For companies and teams, it also supports self-hosting models in a cloud environment.
Go to the console and run the pre-generated script to create a cloud Kubernetes cluster with the model deployed.
Very simple, but also expensive to run long term.

![](/img/kimchi-self-hosted.png)

The final self-hosting option is to deploy a model to an existing Kubernetes cluster connected to Cast AI — the creators of Kimchi.
I didn't get a chance to test this because the agent wouldn't install on my bare metal clusters.
It seems they only support cloud environments, but hopefully this type of thing could expand in the future.

## The bad stuff

The kimchi harness had issue for me in my months of testing.
I highlight the biggest issues in the video, but at one point the harness wasn't just unusable, it made my whole computer freeze if kimchi was running in any terminal.
I had to stop using it until a workaround was found and later a fix was deployed.

That is fine for my personal testing, but if a company or team depended on kimchi features, it wouldn't be acceptable.
At this point I prefer [opencode](https://opencode.ai/) as a harness, but things are still changing fast in this space so I don't expect that to last very long.

In the past I had used Claude's and [exe.dev](https://exe.dev)'s remote environments for coding sessions from my phone, and I felt they were useful.
Kimchi's `/teleport` option isn't as much of a mobile-friendly experience and more of a stopgap for keeping agents running even when your laptop lid is closed.

## Who is it for?

I'm on the $20/month coder plan.
If you use the code `JUSTIN25` when you sign up you'll get an extra $25 worth of credits.

The main question is, is it worth it?

Obviously the answer is, it depends.

None of the open weight models are as good as frontier models.
But we've already mentioned that not everyone needs frontier models.

You can get access to similar open weight models and many more from other services like OpenRouter.
So this doesn't make sense to use for _only_ getting access to open weight models.

The kimchi harness is fine, but I wouldn't call it "enterprise grade".
You can still use the Kimchi models with other harnesses, but you can do that with OpenRouter too.

The self-hosting aspects _I think_ are truly unique to Kimchi (please let me know if other services allow for this).
**But** right now they're coupled to hyperscaler cloud environments, so if ownership and privacy is a requirement, it's still not the right solution.
Even if the instances run in your VPC, I worked at AWS, and I wouldn't consider that private.

So I'm stuck figuring out when I'd recommend someone use Kimchi vs other solutions.

The coder plan seems to last longer than other model services I've paid for, and when coupled with a better harness, the open weight models can offer decent coding performance.
The usage tracking is great for a team, but unnecessary for an individual.

So after thoroughly using Kimchi for a couple months on various personal projects, my recommendation is: if you're an individual, it makes a great backup for a primary coding subscription.
But don't rely on the kimchi harness unless it improves or adds more unique features.

When big AI providers were down, kimchi models were working great.
When I wanted to double-check a plan or PR, opencode with kimchi models helped a lot.
It would be even more useful if automatic model routing didn't depend on the kimchi harness and if self-hosting worked outside cloud environments.
